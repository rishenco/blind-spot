# RoboCup: ближайший работающий аналог нашей задачи

*Ресерч, дата обращения ко всем ссылкам — 2026-08-25.*

## Почему это релевантно

RoboCup Soccer Simulation 2D (SS2D) — это буквально наша задача, только со зрением вместо
слуха: 11 агентов, у каждого узкий FOV (90°), позиция объектов приходит с ошибкой,
пропорциональной дистанции, дальние игроки приходят **анонимными**, канал связи между своими
жёстко ограничен по битам, и всё это должно решаться за 100 мс на агента. Лига живёт с 1997 г.,
и её базовый код (agent2d/HELIOS) открыт и читается за вечер. Standard Platform League (SPL,
B-Human) — то же самое, но с настоящими роботами и подробнейшими техотчётами.

Это единственная известная мне область, где «честный агент с частичной наблюдаемостью,
играющий в командную игру в реальном времени» существует не как статья, а как 25 лет
эксплуатации.

## 1. Модель сенсора в SS2D — прямой прецедент для нашей таблицы громкости

Источник: [RoboCup Soccer Simulator manual, гл. 4 «Soccer Server»](https://rcsoccersim.readthedocs.io/en/latest/soccerserver.html)
(получено через WebFetch, 2026-08-25).

Ключевые параметры и их значения по умолчанию:

| Параметр | Значение | Смысл |
|---|---|---|
| `visible_angle` | 90° | конус зрения |
| `visible_distance` | 3.0 м | радиус «чувствую рядом» вне конуса |
| `quantize_step` | 0.1 | шаг квантования дистанции **в логарифме** |
| `unum_far_length` | 20 м | дальше — номер игрока виден с убывающей вероятностью |
| `unum_too_far_length` | 40 м | дальше — номер не виден вообще |
| `team_far_length` / `team_too_far_length` | до размера поля | то же для принадлежности к команде |
| `audio_cut_dist` | 50 м | дальность слышимости `say` |
| `say_msg_size` | 10 байт | размер сообщения |
| `hear_max` / `hear_inc` / `hear_decay` | 1 / 1 / 1 | **одно сообщение от команды за такт** |

Две вещи отсюда важны нам прямо.

### 1.1 Ошибка локализации пропорциональна дистанции — и это не новость, это норма

Классическая (квантизационная) модель сервера:

```
Quantize(V, Q) = ceil(V / Q) * Q
d' = exp( Quantize( log(d), quantize_step ) )
d'' = Quantize( max(0, d - (d - d')), 0.1 )
```

Квантование в логарифме с шагом 0.1 означает бины с отношением границ e^0.1 ≈ 1.105, то есть
**относительная ошибка дистанции ≈ ±5 % на любой дальности**. С версии 19 сервера доступна
гауссова альтернатива с `dist_noise_rate = 0.0125` (σ ≈ 1.25 % дистанции).

Вывод для нас: предложенная в `doc/ai/brief.md` модель `σ ≈ 0.06·d` (6 %) лежит ровно в том
же порядке, что и 25-летняя практика лиги, и даже чуть «шумнее». Брать можно, обосновывать
дополнительно не нужно.

**Но** — см. §1.3 ниже про то, как эту ошибку генерировать. Это важнее, чем её величина.

### 1.2 Анонимность источника — тоже норма, и она решена

В SS2D игрок дальше 20 м приходит без номера, дальше 40 м — вообще без команды («какой-то
игрок вон там»). Это ровно наш `anonymousSources`. Как это решается в базовом коде — §3.

### 1.3 Чего в SS2D нет и что нам придётся решить самим: временна́я структура шума

В SS2D шум перегенерируется **на каждое наблюдение независимо**, и это безопасно, потому что
наблюдения приходят 6–7 раз в секунду и агент их фильтрует Калманом — лига с этим живёт.

У нас ситуация другая и опасная: концепт говорит, что **мяч — непрерывный излучатель**
(постоянная оценка позиции с той же ошибкой по дистанции). Если реализовать это как
независимый белый шум на каждом кадре при 60 Гц, то бот со скользящим окном 0.5 с усредняет
30 сэмплов и уменьшает ошибку в √30 ≈ 5.5 раза. При d = 10 м человек видит дрожание ±0.6 м,
а бот — ±0.11 м. Радиус ловли 1.2 м, окно ±0.18 с: это разница между «ловит через раз» и
«ловит всегда». Ни одна ручка из `brief.md` этого не ловит.

**Рекомендация (важная):** ошибка локализации должна быть не белым шумом, а **медленно
плывущим смещением** — процесс Орнштейна–Уленбека / на источник-наблюдателя своё смещение с
временем корреляции τ ≈ 0.5–1.0 с:

```
bias ← bias * exp(-dt/τ) + N(0, σ(d) * sqrt(1 - exp(-2 dt/τ)))
observed = true_pos + bias
```

Тогда усреднение по времени не помогает ни боту, ни человеку, и σ(d) означает то, что вы
думаете, что она означает. Это буквально первое, что я бы поменял в спеке восприятия.

## 2. Негативная информация в SS2D: `checkGhost` из librcsc

Файл `rcsc/player/world_model.cpp`, метод `WorldModel::checkGhost(const ViewArea&)`
(librcsc, LGPL-3.0, https://github.com/helios-base/librcsc, клонирован 2026-08-25).

Логика целиком:

```
для каждого отслеживаемого объекта O:
    если O не наблюдался в этом цикле
       и O.posCount > 0                       // мы его не видели прямо сейчас
       и varea.contains(O.pos, angle_buf=5°, VIS_DIST2):   // но ДОЛЖНЫ были
            O.setGhost()                      // ++ghostCount
            если O анонимен и posCount >= 10 и ghostCount >= 2:
                удалить O
```

где `VIS_DIST2` — квадрат **уменьшенного** радиуса видимости:

```
VIS_DIST2 = (visible_distance - |v_self|/decay * 0.1 - 0.25)^2
```

Три инженерных приёма, которые надо украсть дословно:

1. **Сенсорная зона для негативного апдейта сжимается, а не берётся честной.** Вычитается
   запас на собственную скорость и константа 0.25 м, к углу добавляется буфер 5°. Это прямая
   реализация главного тезиса Hoffmann et al. (§4): негативная информация ломает всё, если
   бывают ложные негативы, поэтому «зона, где я гарантированно бы увидел» должна быть строго
   меньше реальной зоны сенсора.
2. **Забывание не мгновенное, а по счётчику.** Один «призрак» — снижаем доверие, два —
   вычёркиваем. Мгновенное удаление по первому же «не увидел» даёт мигающее убеждение и,
   как следствие, мигающее поведение.
3. **Уверенность = целое число тактов с последнего наблюдения (`posCount`), а не ковариация.**
   Сортировка кандидатов идёт по `posCount + ghostCount * 10`. Дёшево, детерминированно,
   отлично отображается в отладочный оверлей. Для нашего дебаг-требования «сколько этому
   убеждению секунд» это ровно то, что нужно.

## 3. Data association на анонимных наблюдениях: `PlayerObjectUpdater`

Файл `rcsc/player/player_object_updater.cpp`. Алгоритм (в порядке выполнения):

**Шаг 1 — гейтинг по достижимости.** Наблюдение `seen` может относиться к треку `old` только
если

```
dist(seen.pos, old.pos)^2 <= ( vmax * dash_noise * count      // куда он мог уйти за count тактов
                             + self_error                      // 1.2 м, ошибка собственной позиции
                             + sensor_error * 3.5 )^2          // 3.5σ наблюдения
```

(константы 1.2 и 3.5 в коде помечены как `magic number` — это честная эмпирика, не теория).
Плюс жёсткий фильтр: если у трека известен номер и у наблюдения известен номер и они разные —
кандидат отбрасывается сразу.

**Шаг 2 — однозначные пары.** Пока есть трек ровно с одним кандидатом или кандидат, доступный
ровно одному треку, — фиксируем эту пару, вычёркиваем из всех списков, **перезапускаем цикл**.
Это классический constraint propagation, и он снимает 90 % случаев бесплатно.

**Шаг 3 — оставшаяся неоднозначность решается полным перебором.** `create_combination()`
рекурсивно перебирает все сочетания оставшихся треков и кандидатов, `evaluate_combination()`
считает **среднеквадратичное расстояние назначения**, берётся минимум. Это Global Nearest
Neighbour, вычисленный брутфорсом, потому что после шага 2 остаётся 2–3 объекта.

**Почему это ровно наш случай.** У нас соперников двое, и мяч звучит всегда — значит носитель
мяча локализован, и в типичной ситуации **неизвестен ровно один соперник**. Полный перебор
назначений для n ≤ 2 — это 2 варианта. Ни JPDA, ни MHT здесь не нужны (см. `belief-tracking.md`).

## 4. Как SPL (B-Human) держит мир: разные фильтры на разные объекты

Источник: [B-Human Team Report and Code Release 2019](https://b-human.de/downloads/publications/2019/CodeRelease2019.pdf)
(скачан и распарсен, 2026-08-25), гл. 5; актуальная документация —
[docs.b-human.de/coderelease2025](https://docs.b-human.de/coderelease2025/) и
[.../modeling/self-localization](https://docs.b-human.de/coderelease2023/modeling/self-localization/).

Главное наблюдение: **B-Human не использует один фильтр на всё.** Под каждую задачу — свой,
самый дешёвый достаточный:

| Объект | Представление | Почему так |
|---|---|---|
| Своя поза | 12 UKF-гипотез, управление гипотезами — частичный фильтр (12 частиц) | мультимодальность бывает редко, но бывает (симметрия поля) |
| Мяч (локально) | **12 калманов**, разбитых на 2 набора по 6: «катится» и «стоит». Наблюдение подаётся во все, для вывода берётся лучший по совместимости+дисперсии. Худший в каждом наборе каждый кадр сбрасывается и переинициализируется | KF не умеет мультимодальность; так её эмулируют дёшево. Ковариация измерения зависит от дистанции |
| Препятствия (роботы) | **EKF на каждое препятствие**, ассоциация — ближайший по евклиду, новый трек только после N измерений за окно, удаление если не виден, хотя должен быть в FOV | классический MTT-минимум |
| Мяч (командный) | кластеризация присланных моделей по порогу расстояния + взвешенная сумма; вес = валидность локализации × свежесть × ожидаемая точность по дистанции; берётся самый большой кластер | устойчиво к одному сошедшему с ума роботу |
| Покрытие поля | **сетка 0.5 м с таймстемпом на ячейку** | см. §5 |

Прямой урок для нас: не надо выбирать «частицы ИЛИ гауссианы ИЛИ сетка». Надо взять сетку
там, где нужна негативная информация и мультимодальность (соперник), и калман там, где объект
наблюдается непрерывно и нужна скорость (мяч).

## 5. Field Coverage: негативная информация как сетка возраста + командный обмен

B-Human 2019, §5.4. Это самая близкая к нам конструкция во всём RoboCup.

- Поле режется на сетку ячеек 0.5 × 0.5 м (в тексте — «квадрат площадью 0.25 м²»).
- Каждый кадр FOV проецируется на поле; ячейки, чей центр попал в FOV **и не в «тень» от
  другого робота**, получают текущий таймстемп.
- Ячейка, по которой прошёл мяч (по `BallModel`), сбрасывается в ноль — «мяч мог быть здесь,
  ищите вдоль его последнего пути». Это ровно то, чем должен быть наш след звукового события.
- Голова робота при поиске направляется на ячейку с самым старым таймстемпом.
- Глобальная сетка = поячеечный максимум по таймстемпу из своей и всех присланных.

Про полосу пропускания: 4-байтные таймстемпы на 6×9 м / 0.25 м² = 864 байта на такт, что не
влезает в лимит правил. Решение: шлётся **один общий таймстемп + по 2 бита на ячейку**
(«видел за последнюю 1 с / 5 с / 20 с / не видел»), итого 58 байт. Точность падает, поведение
не портится.

Урок: **делитесь возрастом информации, а не самой информацией**, и квантуйте возраст грубо.
Для нашего `teamShare` это подсказка (хотя у нас есть более дешёвый вариант — делиться
событиями, см. `recommendations.md`).

## 6. Слой решений: чем в RoboCup заменяют behavior tree

### 6.1 agent2d/HELIOS: генераторы действий + оценщик состояния (action chain)

Код: `src/player/planner/` в [helios-base](https://github.com/helios-base/helios-base) (MIT).

Архитектура владения мячом:

1. **Генераторы** (`actgen_*`, `*_generator.cpp`) порождают кандидатов: прямой пас, «строгий»
   пас с проверкой перехвата, self-pass (пас себе на ход), кросс, короткий дриблинг, удар,
   отбор. Каждый кандидат — это `CooperativeAction` с полными параметрами (куда, с какой
   скоростью, кому).
2. Каждый кандидат применяется к **предсказанному состоянию мира** (`PredictState`), давая
   новое состояние; от него снова запускаются генераторы → дерево.
3. Лист оценивается статическим `FieldEvaluator`.
4. Берётся цепочка с лучшей оценкой листа.

Бюджеты зашиты в `action_chain_graph.cpp`:

```
DEFAULT_MAX_CHAIN_LENGTH  = 4     // глубина цепочки
DEFAULT_MAX_EVALUATE_LIMIT = 500  // оценок листа на одно решение
```

То есть чемпионские команды 2D-лиги принимают решение, оценивая **≤ 500 предсказанных
состояний за такт 100 мс на агента**. Это очень конкретный ориентир бюджета: наш бот при 10 Гц
решений имеет право на такой же порядок, и это далеко за пределами того, что нужно для 2×2.

Оценщик по умолчанию (`sample_field_evaluator.cpp`) намеренно примитивен: `x` мяча + бонус за
близость к воротам + огромные константы за «мяч в воротах» / «можно бить» + штраф за офсайд.
Вся сила команды — в генераторах и в предсказании, а не в изощрённой оценке. Это тоже урок.

### 6.2 B-Human: Skills and Cards, и почему у карты два условия

B-Human 2019, §6.1. С 2013 по 2017 они использовали единую иерархию CABSL (иерархические
конечные автоматы), и в 2019 явно от неё отказались, разделив на два слоя:

- **Skill** — «как сделать» (принимает параметры, может вызывать другие skill'ы, пишет в
  моторику). Например `GoToBallAndKick(kickPose, kickType, length)`.
- **Card** — «когда это уместно» (без параметров, не пишет в выходные представления, сам
  решает, активироваться ли). Например `KickAtGoalCard` вычисляет, можно ли бить, и вызывает
  skill.

И самая важная деталь:

> Cards have the `preconditions` and `postconditions` methods... The preconditions specify the
> conditions under which the card **can be entered**... The postconditions specify the conditions
> under which the card **should be left**. By default, the postconditions are the negation of
> the preconditions.

В примере из отчёта: вход при `dist < maxGoalDistance`, выход при `dist > maxGoalDistance +
1000 мм`. То есть **гистерезис прошит в саму модель поведения**, а не прикручен сбоку. Для
читаемого бота при шумном убеждении это не опция, а обязательное требование: без разных
порогов входа и выхода бот будет дрожать на границе.

### 6.3 Позиционирование без мяча

- **SBSP (Situation Based Strategic Positioning)**, Reis, Lau & Oliveira, 2001, LNAI 2103,
  с. 175–197. Базовая позиция игрока в формации сдвигается функцией от позиции и скорости мяча
  и от «ситуации»; агент идёт туда, когда считает, что в ближайшее время активных действий не
  будет. Полный текст за пейволлом Springer; описание —
  [web.fe.up.pt/~lpreis/soccer/overview/sbsp.htm](https://web.fe.up.pt/~lpreis/soccer/overview/sbsp.htm).
- В agent2d формации заданы **триангуляцией Делоне** по размеченным вручную примерам
  («мяч здесь → игроки тут»), интерполяция внутри треугольника. Данные лежат в
  `helios-base/formations-dt/`, редактор — `fedit2`.

Для нас важен принцип, а не механизм: у обоих подходов позиция без мяча — **функция от позиции
мяча**, потому что мяч — единственное, что все знают точно. У нас мяч звучит всегда, то есть
это условие выполняется буквально. Разница в том, что нам этого мало: у нас позиционирование
должно ещё зависеть от **убеждения о сопернике и от собственной заметности**, чего в RoboCup
нет вообще.

## 7. Обмен мировыми моделями между агентами

- **SS2D**: 10 байт на сообщение, одно сообщение от команды за такт, дальность 50 м. То есть
  обмен есть, но он на порядок беднее того, что агент знает. Команды кодируют туда позицию
  мяча и одного-двух игроков битовой упаковкой.
- **SPL/B-Human**: робот шлёт **уже отфильтрованную свою позу** и цель ходьбы, и только когда
  изменение существенно; из-за жёсткого лимита сообщений робот может молчать несколько секунд.
  `GlobalTeammatesTracker` держит простой 2D-калман на каждого своего, предсказывает по
  присланной цели ходьбы и корректирует локальными наблюдениями
  ([docs](https://docs.b-human.de/coderelease2025/modeling/tracking-teammates/), 2026-08-25).
- Позиции **своих** не требуют слияния — каждый шлёт свою отфильтрованную позу. Позиции
  **чужих** приходится кластеризовать (ε-окрестность) и сливать калмановским шагом
  (B-Human 2019, §5.3.2).
- Честное признание из документации B-Human 2025: различать своих по номеру на футболке они
  **не реализовали**, а определение цвета команды в зрении ненадёжно. То есть даже у лучшей
  команды SPL data association своих не решена до конца.

## Что берём / что не берём

**Берём:**

- `checkGhost` целиком как модель негативного апдейта: сжатая сенсорная зона + буфер по углу +
  счётчик призраков вместо мгновенного удаления.
- Двухфазный data association: гейт по достижимости → однозначные пары с перезапуском →
  полный перебор с минимизацией средней квадратичной невязки. Для n ≤ 2 это тривиально дёшево.
- Целочисленный «возраст наблюдения» как основную метрику уверенности, рядом с непрерывной.
- Field Coverage как модель «где я давно не слушал», и мысль «след движущегося объекта
  сбрасывает возраст ячеек вдоль пути».
- Skills/Cards с раздельными pre/post условиями — гистерезис по умолчанию.
- Архитектуру «генераторы кандидатов → предсказание → статический оценщик» и её бюджеты как
  ориентир (≤ 500 оценок на решение — с огромным запасом достаточно).
- Принцип «делись возрастом, грубо квантованным», если решим шарить сетки.

**Не берём:**

- Триангуляцию Делоне для формаций и SBSP как таковой: у нас 2 игрока и нет позиционной
  структуры, которую стоило бы размечать руками. Идея «позиция как функция от мяча» берётся,
  реализация — нет.
- 12 калманов на мяч: у нас мяч наблюдается непрерывно и его динамика известна (отскоки от
  стен), мультимодальность возникать не должна. Один фильтр + честная обработка отскока.
- UKF/частицы для собственной позы: мы знаем свою позу точно, это не наша задача.
- Битовую упаковку командного канала: у нас нет лимита полосы, есть только вопрос дизайна
  «сколько бот имеет право знать от напарника» — это ручка `teamShare`, а не инженерная
  проблема.
- Модель шума SS2D (независимый шум на наблюдение) — см. §1.3, для непрерывного излучателя
  при 60 Гц она даёт боту незаслуженное преимущество.
